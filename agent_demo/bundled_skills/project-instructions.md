# 维护项目指令文件（AGENTS.md）

这是 agent 自带的手册（跟着 agent 走，任何工作区都能取到）。项目指令文件是**那个
工作区**的长期约定：跨会话、跨工具、可进版本库。它和会话日志分工不同——日志负责
"这次会话发生过什么"，指令文件负责"这个项目一直是怎么做的"。**不要用日志替代它，
也不要用它记录一次性的事**。

## 什么时候创建

当工作区里还没有 `AGENTS.md`（模型上下文里会明确指出这一点），而你已经掌握了
**稳定、可复用**的项目知识时——通常是首轮任务做完之后。创建前先向用户说明打算写
哪几节，等用户批准（写文件走 approval，不要静默创建）。

## 什么时候更新

只沉淀"下次还会用到"的东西：

- 反复用到的运行 / 测试 / 检查命令（以及它们的坑）
- 目录结构与依赖方向、模块职责边界
- 代码风格、命名、提交信息约定
- 用户明确要求长期遵守的偏好或禁忌（"这个目录不要动"）
- 你踩过并验证过的坑（附上证据，比如命令与输出）

**不要写**：一次性调试输出、临时任务状态、进度百分比、密钥/token/凭据、
未经验证的猜测、从别处抄来的通用建议（那种东西每个项目都一样，等于噪音）。

## 最小骨架

```markdown
# AGENTS.md

<一句话：这个项目是什么>

## 命令

# 必须怎么跑（含环境：conda / venv / docker；质量门：lint / type / test）

## 架构

# 目录结构 + 依赖方向（谁可以 import 谁）+ 关键不变式

## 约定

# 代码风格、命名、注释语言、提交信息、评审要求
```

按需保留小节：不存在的部分宁可空着，也不要写"待补充"占位——模型读到空话
会以为那就是全部约定。

## 改已有文件的规矩

- 改之前先读全文，**保留用户已经写下的明确规则**，只增补或修正。
- 你的发现和文件里写的冲突时，先问用户"以哪个为准"，不要直接改文件。
- 一次只改必要的一小节；不要把整份文件重排、重写。
- 改完在回复里说明改了哪一节、为什么。

## 长度

指令文件每轮都在 system 前缀里（有字符预算，超了会被截断）。保持在几十行
量级：具体到"怎么跑"和"别踩什么"，而不是复述代码能自证的东西。
