fix(loop): 认领与落盘原子化——取消不再静默吞掉用户消息（P1-2）

旧顺序是 `claim()` → `await pre_step` → 落 `user/message`：认领先把消息从队列
摘掉，而取消点夹在"摘除"与"落盘"之间。实测（探针让 pre_step 挂 5 秒再取消）：

  spliced: None removed=1 target=next-turn   ← 认领摘掉了消息
  取消后：队列 [] · surface 无 user 消息 · 日志无 outcome=canceled

那条消息三处都不在，`Agent.cancel()` 的 `inbox.clear()` 也救不回来（它不在队列里了）
——用户原话静默消失，事后无法审计。这是不变式①的反例：一次"摘除"发生了却没有记录。
同源还有第二个窗口：user/message 落盘后、`await _resolve_request` 前取消，会留下
"有用户消息、没有请求"的半提交。

**修法：把两个 await 都提到 claim 之前**，让"认领 → step/start → user/message"
成为没有 await 的原子区：

  pending = inbox.peek(target)          # 只读候选，不改队列
  messages = await _resolve_pre_step()  # 取消点（队列未动）
  config = await _resolve_request()     # 取消点（队列仍未动）
  # ---- 以下无 await：一次性提交 ----
  inbox.claim(target, turn) → step/start → user/message

取消语义因此确定：落在钩子里 → 队列一字未动，clear() 走正常路径留 `outcome='canceled'`；
落在提交后 → "真的开始了这一步、随后被中断"，消息已在日志里（不是半提交）。

配套三处：

- `Inbox.peek(target)`（新，state/inbox.py）：只读候选，批次规则与 claim 逐字一致
  （先整个 next-step、再从 next-turn 取一条），否则"钩子看到的"与"真正认领的"会漂
- `_run_step` 收 run_turn 解析好的 config；重试时函数内**重新解析**（重试要按当时的
  钩子取路由，不能用失败前那份快照）
- pre_step 拒绝（返回 None）时**也消费批次**：拒绝的语义是"这条不发给模型"，不是
  "留着下次再问"——不消费会让 has_pending 恒真，状态机拿同一条消息无限空转
  （实测：测试 40 秒不返回）

测试两条新用例（tests/test_loop.py）：pre_step 里取消 → 日志有 canceled 记录、
消息没进 derive_messages、turn/end 记 aborted；模型已开始流式后取消 → 那条
user/message **在**（提交后取消不是半提交）。
