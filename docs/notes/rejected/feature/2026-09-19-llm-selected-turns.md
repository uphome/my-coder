# Agent Note: 不让 LLM 从清单里挑回合

Status: rejected — 它会把"模型能不能自己找回信息"这件事测没，且实测选择准确率低于字面基线

## Problem

给模型一个被压缩过的上下文，再让它回答依赖被压内容的问题——**怎么给它历史？
怎么量它找回来了？** 一个很自然的方案是两段式：

1. 先用一次 LLM 调用，把历史回合清单交给它，让它**挑出相关的那几个回合**；
2. 把挑出来的原文喂给它，再让它回答。

这个方案同时看起来能当**机制**（省上下文：只读回相关的）与**评测方法**
（"挑对了"就是"找回来了"）。

## Decision

**不用它，两个位置都不用。**

- **评测上**：判据改成**端到端**——模型自己在真实工具面（`session_manifest` → `read_turn`）
  里找到答案并把任务做对。**我们不替它表述需求，也不替它挑回合**：只给任务，
  看它找不找得到。选择类题目降级为**组件诊断**（只在需要定位"是清单不好用还是模型不会用"
  时才跑）。
- **机制上**：检索面保持**全量**（曾经进过上下文的事件），导航靠"顺序 + 回合号 + 足迹"，
  由模型自己决定读哪个回合。不做相关性排序，也不做"先让 LLM 选一遍"。

## Alternatives considered

这就是被否决的那个方案本身。否决的理由有四条，其中两条是实测：

1. **测量效度**：如果由我们（或另一个 LLM 调用）先挑出回合，那么被测对象就变成了
   "选择器准不准"，而真正想知道的是"**模型自己能不能意识到缺东西、能不能找回**"。
   把需求替它表述掉，就永远测不到第 ① 步（意识到缺口）。
2. **锚点能力被偷换**：选择题的题面必须包含一个能定位的线索，而**题面里写什么，
   就等于我们告诉了模型什么叫"相关"**——这正是设计里明确不要的东西（"不是通过我们
   给出我们想要什么，让 LLM 来挑回合"）。
3. **实测：LLM 选择还不如字面基线**。13 道导航题（给定一个线索，选出它属于哪个回合）：
   LLM top-1 **38%** / ±1 **46%** / top-3 **38%**，字面（词法）基线 top-1 **69%** /
   ±1 **85%** / top-3 **69%**。这份对比自身有三个混淆（题目要求锚点逐字出现 → 偏袒字面法；
   "结论摘录"既是题面来源又是提示；生成时关了 thinking），所以它**不足以**证明
   "LLM 不会导航"——但足以说明**它不是一个可以拿来当评测骨架的可靠组件**。
4. **多一次有损环节**：选择器的输出是"哪些回合相关"的压缩表示，一旦选漏，
   后面的原文阅读再准也没用——把一个不可控的有损环节插进本来无损的链路里。

**保留这篇的理由**：这个方案足够自然，下一个想改召回的人很可能重新想到它。
理由写在上面，省得再试一遍。

## Consequences

- 评测成本变高：端到端要真跑 agent（每次 5~15 个请求），而不是一次选择调用。
- 结论只能是定性的（存在性 + 情境档案），见
  [验收方法学](../../implemented/testing/2026-09-19-context-recall-evaluation.md)。
- 换来的是**被测对象没被替换**：测的就是"模型自己能不能找回被遮蔽的信息"。
