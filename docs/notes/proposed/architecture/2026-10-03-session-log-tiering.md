# Agent Note: 会话日志的冷热分层（内存里留投影还是留全量）

Status: proposed

## Problem

**内存与"总历史"绑定，而不是与"活跃上下文"绑定。** 实测（2026-10-03，冻结快照
`.eval/snapshots/web-1788604766-frozen.jsonl`，111.7 MB / 425,985 事件）：

| 指标 | 数值 | 怎么量 |
|---|---:|---|
| 重放该会话 | 常驻 **217 MB** · 峰值 **590 MB** · **5.2 s**（63.8 MB 年代的实测为 16.2 s） | `load_events` + `adopt` + `tracemalloc` |
| 内存 / 文本 | **≈3.4×**（事件对象带 payload，比 JSONL 文本重） | 同上 |
| 服务私有内存（加载着这一个会话） | **484 MB**（早先 4 个小会话为 337 MB） | `Get-Process` |
| 其中已被判定"不是状态"的帧占比（旧文件） | **98.9% 的行 / 89.3% 的字节** | 按行扫 `"type"` |

三条结构性原因（都不是漏，是决定）：

1. **日志是唯一事实源，且全量常驻**：`Session._log: list[SessionEvent]`；
2. **压缩只改 `_surface`、不动 `_log`**（`app/compaction.py`）——这是**故意的**：召回要能读回
   被遮蔽的原文（见 [召回那篇](../../implemented/feature/2026-09-19-context-recall.md)）。于是上下文能压小，
   **内存不降**；
3. **每个打开的席位各持一份 `Session`**（`web/state.py` 的 `Seat`）。

已止血的两项治的是别的东西，**没有改变"一份会话 = 整份日志在内存里"**：
[#46 ① 冷却席位释放](../../implemented/feature/2026-10-03-seat-eviction.md) 限住**同时打开的会话数**（上限 3），
[#46 ② 事件视图缓存](../../implemented/simplification/2026-10-03-events-view-cache.md) 消掉**每请求的整表拷贝**
（12.1 ms → 0.0 ms）。

**读的那一侧同样没根治**：打开/恢复一个会话要**整份解析 JSONL**（源文件 append-only、
**不重写**是既有决定）。#42 让冷扫描从 6.4 s 降到 0.6 s（行数少一个数量级），但"打开一个
117 MB 的会话"仍然要读完它、并在内存里建 42.5 万个对象。

## 测量修正（2026-10-03，落地阶段 1~2 之后）

**本文原本的"索引常驻 + 冷区"形状，在本仓库当前的数据尺度下是错的**。实测（同一份快照）：

| 方案 | 常驻内存 |
|---|---:|
| 整份重放（改前） | 377.7 MB |
| **按类型过滤重放**（已落地：帧整类不解析、不建对象） | **21.8 MB**（峰值 22.3 MB · 3.0 s） |
| 索引常驻 + 冷区（本文原方案） | **索引本身就要 39.0 MB** |

即：**索引（42.5 万条 × 约 90 字节）比"把该留的 4.7k 条事件物化"更贵**。原因是 #42 之后真正
需要保留的事件只占 **1.1%**，而索引要为**每一条**（含被跳过的帧）付钱。

**因此本项收敛为两条已经落地的机制**：

1. **整类跳过不解析**：`TRACE_FRAME_TYPES`（流式帧）重放时既不解析 payload 也不进索引——
   `scan_index(skip_types=…)` 用行首正则判类型；**守卫不放松**（未知类型仍解析出来判 `ignorable`，
   该拒就拒）；
2. **不在没人读的地方建对象**：`Session.from_path` 是"打开/读取一个会话"的**统一入口**，
   三个入口（服务打开会话 / 改名 / 跨会话召回）都走它。

**冷区（索引常驻、payload 全在磁盘）何时才值得做**——判据写清，免得以后凭感觉重来：

> 当"需要保留的事件数 × 约 500 字节/条"超过"索引成本（约 90 字节/条，按**全部**事件算）"时，
> 也就是**保留比例 > 约 20%** 时，冷区才开始赢。老日志当前保留比例是 **1.1%**（新日志已无帧），
> 所以现阶段**不做**；等出现"单会话几十万条非帧事件"的真实样本，再按下面阶段 3 推进。

**所以现在的处境**：一个长期使用的会话，每次打开都付"整份读 + 全量对象"的代价；
而这个代价与"模型此刻需要多少上下文"完全无关。

## Proposal

判据一句话：**内存里只留"模型此刻需要什么 + 定位其余内容所需的索引"，其余按需从磁盘读。**

### 一、事件存储分三层

| 层 | 内容 | 大小量级 |
|---|---|---|
| 投影 | `_surface`（模型可见顺序，seq 列表） | 与回合数同阶（本例 138 项） |
| **索引** | 每条事件一条 `(seq, type, turn, step, offset, length)`——**不含 payload** | 与事件数同阶，但每条几十字节的定长值 |
| **热区** | 最近 N 个事件（或最近 K 个回合）的**完整事件对象** | 与"活跃上下文"同阶 |

冷区的 payload 留在 JSONL 上，需要时按 `(offset, length)` **单条**读回并解析。

### 二、读路径：从"整表"改成"游标 + 定点"

`Session.events` 现在同时扮演两个角色——"给我全部事件"（历史/压缩/审计）与
"我只要新增的那段"（每请求投影）。改成两个明确接口：

- `events_since(index)`（已有）——增量投影；
- `event_at(seq)` / `scan(start, stop)`——**定点取原文**，走索引到磁盘读。

`events` 的旧语义（整表元组）**降级/移除**：它的 15+ 处消费者要在同一批改动里迁完
（不能一半旧语义一半新语义）。

### 三、写入不回退

`append` 仍然"校验 → 落日志 → 改投影 → 通知订阅者"，只是**不再永久保留 payload**：
超过热区就只留索引。这**加强**了不变式③（磁盘 ≥ 内存），也不动不变式①（没有状态不进日志）。

### 分三阶段（每阶段独立可验收）

1. **索引化重放**（低风险）：`load_events` 第一遍只解析 `type` 与字节偏移，**不建 payload**；
   谁要哪条再解析哪条。收益：打开会话不再一次性造 42.5 万个对象。
2. **冷热分界**：超过 K 个回合的事件只留索引，热区保留完整对象。
3. **接口统一**：把三类消费者（召回 / 压缩 / Web 历史）迁到 `event_at` / `scan` / `events_since`。

## Alternatives considered

- **只维持已止血的两项，不动结构**——**否决**：打开大会话仍要整份读 + 全量对象，且**不随 #42 改善**
  （旧文件已经那样；新文件只是不再新增帧）。长期使用的会话只会越来越慢。
- **定期把日志重写成"只有 surface"的新文件（丢弃被遮蔽的原文）**——**否决**：那会拆掉召回的
  地基（"压缩只改变看得见什么，不改变存在什么"），把"能否找回被遮蔽内容"从确定性变成运气。
  这是本仓库最不能动的一条。
- **SQLite / session-query（DSH 走的路）**——**留作后续，不在本期**：它同样解决"按需读"，
  但引入**第二事实源**（JSONL + 数据库）与迁移/一致性问题。本仓库当前规模
  （78 回合 / 42.5 万事件）用"JSONL + 内存索引"足够；判据是"单会话 > 数百 MB 且需要跨会话查询"。
- **内存里只留压缩后的字节（zlib 等）**——**否决**：解压时仍然在内存里造出全部对象，峰值不降，
  治不了"对象数"这个真正的成本。
- **只在 Web 宿主侧截断早期事件**——**否决**：把架构问题推给一个宿主；CLI / 召回 / 压缩仍各自
  面对全量，而"截断"会破坏"日志是唯一事实源"的可重建性。

## Risks

- **接口改动是破坏性的**：`Session.events` 有 15+ 处消费者，必须一次迁到底。
- **召回的"读回原文"是硬需求**：冷区按 offset 读取必须可靠。索引与实际字节不一致时**必须
  fail-closed**（越界 / type 不匹配 → 明确报错），绝不静默返回空——那会把"读不到"伪装成"不存在"。
- **性能可能反转**：热区设得太小，"按需读"会把顺序扫变成随机读。所以验收里**同时**钉内存与
  打开耗时两个数，不能只看内存。
- **多一层就可能不同步**：索引必须是**日志的纯函数**（可从 JSONL 重建），不许成为第二事实源。

## Acceptance criteria

- [ ] 打开 42.5 万事件的会话：**常驻内存降一个数量级**（现在 ≈3.4× 文本量）
- [ ] 同一会话的**打开耗时下降**（现在 5.2 s 重放；旧测 16.2 s）
- [ ] 打开第二、三个大会话的单位成本下降（叠在 [#46 ①](../../implemented/feature/2026-10-03-seat-eviction.md) 的席位上限之上）
- [ ] **召回仍能读回被遮蔽区间的原文**：用现成的可恢复性审计脚本回归（`eval/recall/audit_recoverability.py`）
- [ ] **压缩仍能选段与生成摘要**：`tests/test_compaction.py` 全绿
- [ ] 定点读取有**机械测试**：任意 seq 取到的原文 == 直接解析该行
- [ ] 索引与日志不一致时 **fail-closed**（明确报错，不静默）
- [ ] 三绿（`ruff` 含 `eval` · `mypy` · `pytest`）+ 本文档从 `proposed/` 移入
      `implemented/architecture/`（`## Proposal` 改 `## Decision`，补 `## Testing`）
