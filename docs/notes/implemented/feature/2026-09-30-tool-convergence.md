# Agent Note: 工具收敛——按"无进展只读调用"给工具面加收敛压力

Status: implemented

## Problem

开放任务里 agent 会"再查一下"到停不下来：issue #2 的实录是**单回合 15 次模型请求、
24 次工具调用**才给结论。这不是死循环（每轮读不同东西），而是**工具面缺少"够了"的信号**。

实测（真实语料 4 个会话 / 57 个有工具调用的回合 / 435 次调用，零 LLM）：把每个回合切成
"连续纯读调用段"（期间没有任何 `edit`/`write_file`/`bash`），得到

| 指标 | 值 |
|---|---|
| 最长只读段 | p50 **1** · p90 **8** · **max 39** |
| 最长只读段 ≥ 8 的回合 | 6 个（11%），涉及 **148 次调用（占 34%）** |
| 最长只读段 ≥ 10 的回合 | 4 个（7%），涉及 **132 次调用（30%）** |
| 极端 | `web-1788604766` 回合 32：**39 次调用全是只读**；回合 1：30 次里 24 连读 |
| 对照：61 步的**实现型**回合 | 最长只读段 **4**（全程在改代码/跑测试） |

**这条分界线是关键**：要修的是"读了很多、什么都没产出"，而"边改边验"的大任务是合法的。
所以判据不能是回合总步数（会砍掉后者），只能是**自上次变更以来的连续只读调用数**。

**测量口径的教训（留在文档里，避免重犯）**：本问题最初被描述成"29 次重复调用"，
用**完整参数**重量后只有 **2 次**（全语料重复调用占 2%，去重只值 2/435）。差异来自
比较前把参数截断到 70 字符——**截断会把"看起来一样的调用"放大 15 倍，而口径错了会选出
完全相反的设计**（去重 vs 收敛）。

## Decision

机制落在**工具层**，靠声明而不是靠循环里的业务判断。

### 一、`ToolSpec.cacheable`：声明这次调用算不算"只读、无产出"

- 新增字段 `cacheable: bool = False`；只有**纯读**工具声明为 `True`：
  `read_file` / `grep` / `glob` / `list_files` / `session_manifest` / `read_turn`。
- 注册时刻校验：非布尔值抛错；`requires_approval=True` 的工具声明 `cacheable=True` 抛错
  （有副作用却号称只读 = 自相矛盾，宁炸勿静默）。
- 判据与 `execution_mode`/`offload` 同源：**"它会不会改变工作区"**，由工具作者声明。

### 二、`ProgressPolicy`：有状态的无进展计数（纯逻辑，状态层）

- 位置 `state/progress.py`；`note(flags: list[bool]) -> 'close' | 'nudge' | None`：
  全是 `True` → 只读计数 +1；出现 `False`（有一次变更类调用）→ **清零**。
- 阈值可配：`nudge_at=8`（软）、`close_at=16`（硬）、`enabled` 开关。
- 每个回合开头 `reset()`（回合是收敛的边界）。

### 三、软信号写进**那次工具结果**的正文

计数到达 `nudge_at`（以及其后每 4 次）时，在**该次 `tool/result` 内容末尾**追加一行：

> `⚠️ 已连续 8 次只读调用、期间没有任何改动或产出。若关键事实已验证，先给结论；要继续深挖，请说明还缺什么。`

写进结果正文的理由：它进日志（可重建、可审计）、就在模型刚拿到的输出里（比状态栏更贴近
决策点），且不动 system 前缀（不破坏缓存）。

### 四、硬边界：一步"只出文本"的收尾步

计数到 `close_at` 时，**下一次请求**：

- `tools=()`（本次请求不带工具面）；
- 叠一条收尾指令（合成 user 消息，与运行时状态同一通道）："本回合的只读调查已达上限。
  请不要调用工具；给出现在能给的结论、列出未完成的部分与建议的下一步。"
- 该步结束后一律收尾，`turn/end` 的 reason 记 **`read-budget`**（可统计触发率）。

**绝不在带工具调用时硬截断**：那会留下"有 tool_calls 却没有结果"的 assistant 消息，
wire 非法（既有不变式的邻居）。收尾步是**合法的一步**，模型仍有完整表达能力。

### 五、接线（不写业务 if 进循环）

- 计数与判定在 `ProgressPolicy`；循环只做三件事：把本步调用的 `cacheable` 标志交给它、
  把返回的软信号附加到结果正文、在它要求收尾时用空工具面构造请求。
- 收尾指令的**文本**由 `app/factory.py` 传入（与 `RECALL_DISCIPLINE` 同源），
  `state/` 只持有逻辑、不持有文案。
- `enabled=False` 或两个阈值都设为 `None` = 完全回到今天的行为（可关）。

## Alternatives considered

- **按回合总步数设上限**（opencode 的做法：`agent.steps`，"before forcing text-only
  response"，默认 `Infinity`）——**否决**。实测实现型长回合的最长只读段只有 4，
  但它有 61 步：按步数砍会砍掉合法的大任务。DSH 与 PI 都不设上限（DSH 的 step 循环是
  `while (true)`，暴露的设置只有 `maxParallelToolCalls`；`maxTokens` 只是单次输出上限）。
- **机械去重**（同一 `(name, args)` 且期间无变更 → 不重跑）——**否决**。
  实测只有 2/435 次满足，收益远小于它引入的语义风险（模型会怀疑"我刚改过，为什么读到旧的"）。
- **只在提示词里加收敛纪律**——**单独用不够**。`Economy` 已经写着"never repeat a call
  you already made"，而实测仍有 15~39 次连读：纪律无法在**决策点**上给模型反馈。
  机制给的是**局部、及时、有计数**的信号。
- **把软信号放进运行时状态栏**——**部分否决**。状态栏每请求都在、会一直出现，
  而收敛压力应该只在"确实在打转"时出现，否则就是每轮都付的噪声。
- **按 token 预算收敛（M2 的做法）**——**留给 issue #3 的 M2**。两者判据不同
  （剩余额度 vs 无进展步数），但通道相同；本 note 只做前者，避免把"预算水位"做两遍。

## Testing

**单元测试（零 API，`tests/test_progress.py` 10 条）**：声明校验（非布尔值 / `requires_approval`
与 `cacheable` 同时为真 → 注册时刻抛错）、计数与变更清零、提示不刷屏（第 3 次与之后每 4 次）、
收尾只请求一次、关掉开关后与加机制前逐项一致（工具面 / 无提示 / `turn/end` 仍是 `completed`）、
软信号确实写进**那次**结果正文、收尾步的请求 `tools` 为空且含收尾指令、`turn/end` 记
`read-budget`、**收尾步里模型若仍发工具调用则不被执行**（补 is_error 结果，保证 wire 成对）。

**A/B（真跑，2026-09-30，同一只读调查任务 × 开关各 2 次）**：

| 会话 | 模型请求 | 工具调用 | 最长只读段 | 软提示 | 收尾步 | 关键事实覆盖 |
|---|---:|---:|---:|---:|---|---|
| 关闭 r1 / r2 | 9 / 10 | 12 / 19 | 7 / **17** | 0 / 0 | — | L0/L1/L2 + 两个工具名 |
| 打开 r1 / r2 | **7 / 6** | **11 / 9** | 10 / 8 | 1 / 1 | — | 同上（结论更短：3.2k/4.0k 字 vs 3.9k/4.2k） |

- **请求数 −30%、工具调用 −35%，结论质量没有下降**（四轮都命中关键事实：三层各自的实现、
  两个工具名、至少一处边界）。
- **软提示就收住了，硬边界一次都没触发**——这是设计意图：软层管用就不动硬层。
  关闭组 r2 的 17 连读正是 issue #2 形状的那类回合。
- 复现：`conda run --no-capture-output -n agent-demo python -m my_coder.cli --workspace .
  --sessions .eval/convergence --session conv-<on|off>-r<N> --compact-at 0 [--no-convergence] "<任务>"`

**这条证据的边界**：n=2/组、单一任务与模型，只能说"这道题上有效"；质量判据是关键词覆盖 +
人工粗看，不是严格判分；**硬边界的真实行为只有单元测试证据**（A/B 里没触发）。

## Consequences

**换来的**：开放任务的只读调查有了机械可判的收敛压力（判据来自声明，不是工具名硬编码），
请求数与工具调用数下降约三分之一，而"边改边验"的大任务完全不受影响（一次变更就把计数清零）。
软信号进日志、可审计；收尾步是合法的一步（不产生非法 wire），`turn/end` 的 `read-budget`
让触发率可统计。机制可整体关掉（`--no-convergence`），阈值可按宿主调。

**付出的与风险**：

- **阈值误伤**：p90 = 8 意味着约 11% 的回合会触发软信号；若真实任务需要 20+ 次只读才能形成
  结论，收尾步会逼出"不完整但诚实"的答案（它必须列出未完成部分）。阈值可配、可关，
  但**当前默认值是开着的**——这是有意的取舍（本仓库把体验看得比"绝对不打断"更重）。
- **软信号被忽略**：可能被当成噪声，所以硬边界必须存在（否则等于只加了一句提示词）。
- **`cacheable` 声明错**：把有副作用的工具声明成只读 → 计数不清零、可能提前收尾。
  注册校验只挡得住"有 approval 却声称只读"这一种，其余靠评审。
- **新 reason 的语义**：`read-budget` 会进入日志（唯一事实源），按 reason 统计或分类的
  代码必须知道它；前端不处理也不影响正确性（回退成普通收尾）。
