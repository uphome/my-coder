# Agent Note: 上下文召回——压缩只改变"看得见什么"，三层把它补回来

Status: implemented

## Problem

压缩让模型失去对历史的访问，但**日志里一个字节都没少**：`replace` 只改 `Session._surface`
这个索引，`_log` 是只追加的。问题不在数据，在**通道**——模型只有"当前上下文"这一个入口。

三条实测把这件事钉死：

1. **摘要请求只喂 `text` 块**。`app/compaction.py` 构造摘要输入时取
   `[b.text for b in msg.content if type == 'text']`，而工具结果的块类型是 `tool_result`
   ——**工具输出对摘要器完全不可见**。所以"工具有关的精确值（端口、路径、命令、报错串）
   在压缩后消失"不是摘要写得不好，是**确定性**的。实测一次压缩：12 条被压消息里有三段
   工具输出（合计约 4,700 字符），摘要输入只有 474 字符。
2. **小会话压缩会直接失败**：`run_compaction` 有硬门槛 `len(summary) < len(conversation)`，
   而"conversation"只算散文——散文薄的时候摘要有 1.5~2k 字符的结构化地板，
   压缩**直接报错**（实测：2k 的被压区间 → `summary not smaller than content`）。
3. **压缩在真实语料里几乎没发生**：整个 `.sessions`（4 个会话、60 MB、20 万+ 事件）里
   **成功压缩只有 1 次**（那次尝试 4 次，前 3 次 `empty summary`）。
   复现：`python eval/recall/audit_recoverability.py`（零 LLM）。

## Decision

三层把"看得见"与"存在"之间的差补上，全部只**读**日志、不写工作区、不需要 approval。

### 检索面：曾经进过模型上下文的事件

`user/message` / `assistant/message` / `tool/result` 的**全集**，含已被 `replace` 遮蔽的
（`recall.shadowed_seqs`）。痕迹事件（chunk / reasoning / `request/header`）**不进**检索面：
它们从未进过上下文，谈不上损失，而且占了日志 99.6% 的行数。可重建的投影（todo 栏、
上下文状态栏）同样不算损失。

### 三层：L0 会话目录 → L1 用户话清单 → L2 回合明细

| 层 | 形态 | 位置 | 模型怎么用 |
|---|---|---|---|
| **L0** | 运行时状态贡献者（每请求一条合成 user 消息） | `app/factory.py` 的 `_runtime_status()` 注册；渲染在 `app/recall.py` 的 `session_index_text` | 知道"我有历史、当前会话压过几次" |
| **L1** | 工具 `session_manifest` | `app/recall.py` 的 `build_turns` / `render_manifest` | 先看清单，挑回合号 |
| **L2** | 工具 `read_turn` | `app/recall.py` 的 `render_turn` | 再读那一回合的原文 |

L0 只列**同一工作区**的会话（判据是 `session/workspace`；跨区等于把别的项目的会话念给模型）。

### L1 的三条渲染规则

1. **截断必须明说并给坐标**：超 120 字符的用户话补
   `（共 N 字，用 read_turn(turn=T) 看全文）`。实测真会话里 1,269 字的用户话只留 120（**9%**），
   而被砍掉的后半段恰好是"不新增第三方依赖""测试统一用 pytest"这类**约束**——
   设计原则是"用户话是约束来源，绝不能因为压缩就从目录里消失"，只补一个 `…` 等于静默违约。
2. **重复的真人发言不删行、但要标**（真会话 3 组/73 条）：首次标"另有 N 次同句"、
   后续标出处——两条一模一样的行没法区分是哪一次。
3. **没有文本结论的回合写明"（无文本结论）"**，不用 `—`（它同时兼任"字段为空"与
   "确实没有"两种含义，真会话 2/59 个回合如此）。

### L2：按行分页，只有一处截断

`offset` 是 **1 起的行号**（与 `read_file` 同一套心智），`max_chars` 是本次字符预算，
**在行边界停**；显示不全时明说"共 X 行 / Y 字符，本次显示第 A–B 行；继续用 offset=B+1"，
并列出本回合可用的 `step`。块级**不许**再截断（`render_message(limit=None)` 默认不截断）：
截断只允许发生在这一处，且必须自报家门。

### agent 的供给面（工具存在 ≠ 会被用）

模型每轮真正读到的与召回有关的只有四样东西，缺一样都表现为"工具装了但没人用"：

| 供给面 | 放在哪 | 要点 |
|---|---|---|
| **什么时候该回查** | `app/factory.py` 的 `RECALL_DISCIPLINE`，进 `discipline` 段（通用纪律 **Continuity**） | 看不到的既有决定不是"没有决定"；**绝不许**用一个"看起来合理"的具体值把空缺补上——"我查不到"远好过一个自信的错数字 |
| **怎么用** | `app/factory.py` 的 `RECALL_TOOL_SECTION`，进 `tool:recall` 段（order 107） | 先 `session_manifest` 看清单 → 再 `read_turn` 读原文；压缩只改变看得见什么，不改变存在什么 |
| **在需求发生处提醒** | L0 状态栏 | 只在**当前会话**被压缩过时追加一句"被折叠的原文没有被删掉，先看清单再读原文" |
| **工具手册** | 两个工具的 `description` | `read_turn` 的说明写明"长回合按行分页返回，输出会说清总行数、给了哪几行、用哪个 offset 继续" |

三段由 `build_agent(..., recall_guidance=True/False)` **一起开关**：把它与
`recall`（装不装工具）分成两个因子，才能回答"不查是因为没教，还是因为不需要"。

**实测（2×2 实验，每格 2 次）**：把题面换成"真有缺口"（F 必要、且不提示去哪找）之后，
**零供给面**下模型也 **4/4 主动查历史并全做对**；供给面的作用是**抬高查询频率**
（`value-port` 4→6 次、`constraint` 1→4 次），**正确率一格没变**。
所以它的定位是**行为倾向的放大器**，不是"召回可用的前提"。
复现：`python eval/recall/run_endtoend.py --items value-port --arms R3 --guidance off --tag g0 --reps 2`
（花 API；结论与情景设计见[验收方法学](../testing/2026-09-19-context-recall-evaluation.md)）。

### 边界与判据

- **跨工作区不放行**：只允许读同一工作区的会话；跨区返回 `is_error`，**错误里不泄漏对方的目录**。
- **有界**：L2 默认 12,000 字符一页 + 行分页；L1 每行 120 字符 + 结论摘录 60 字符。
- **缓存三条**（L0 每请求求值，必须便宜）：① 扫**别的**会话按 `(mtime_ns, size)` 键控缓存，
   键必须含影响那一行的**所有**输入（含宿主默认工作区——Web 每个 seat 各有默认工作区，
   少这一维会把别的 seat 的归属算成自己的，而跨工作区授权就建在这一行上）；
   ② **当前会话排除在磁盘扫描之外**（它每请求都在长，任何 stat 缓存都会失效）；
   ③ 当前会话由**增量游标**投影，不许碰整表（`session.events` 每次访问拷贝整个元组 ≈20 ms、
   `session.workspace()` 是反向全扫 ≈10 ms）。合计 L0 每请求 0.1~0.2 ms。
- **两个工具 `execution_mode='parallel'` + `offload=True`**：纯读；体内全是同步读盘，
  不卸载会堵住事件循环与超时定时器。
- **工具入参自己较真类型**：注册表不做类型校验，坏值一律降级成 `is_error`
  （`bool("false")` 是 `True`、`bool` 是 `int` 子类、未知 `scope` 不许当默认值）。

## Alternatives considered

- **让 LLM 从清单里挑回合（两段式检索）**：否决。理由与实测见
  [被否决的那篇](../../rejected/feature/2026-09-19-llm-selected-turns.md)。
- **相关性排序 / embedding 检索**：否决。语料是自述的时间线而不是文档堆，排序会把
  "顺序"这个最强的信号换成一个分数；而且排序意味着我们替模型决定什么是相关的。
  导航靠"顺序 + 回合号 + 足迹"，让模型自己走。
- **字面检索兜底（grep 式）作为 v1**：否决。设计期留了实测反例（多条事实在措辞上
  与提问无字面交集）。
- **DSH 的同题提案**：deepseek-harness 有一篇 `proposed/feature/2026-07-06-recallable-compaction.md`，
  走的是**冻结索引 stub + 低频字面锚点 + 状态 checkpoint + `history_read`**：
  每个被压块摘要成一个 ~100–200 token 的索引条目，条目里带"关键词行"（精确报错串、
  配置键），页脚由代码写上 `shadowedRange` 与读取入口。它与我们的取舍正好相反：
  它在**压缩时**付出索引成本，换"模型先看到锚点"；我们在**查询时**付出导航成本，
  换"不加一层有损摘要"。两者都不做相关性排序。没选它的原因是：
  我们的摘要是不可控的（摘要器只看得见 text 块），在上面再叠一层索引会把
  "工具输出里的精确值"埋得更深，而这些精确值正是最需要救回的东西。

## Consequences

**换来的**：模型可以在**不改变压缩行为**的前提下找回被折叠的原文；检索面覆盖全部历史
（含多次压缩叠加）；不引入排序偏见；L0 的成本可控（0.1~0.2 ms/请求）；
`recall=False` 提供了一条忠实的"改造前"基线臂。

**付出的**：

- **模型要自己导航**：多一层认知负担（清单 → 回合 → 分页），且实测"会不会查"取决于
  情境里有没有真缺口，而不是取决于提示词。
- **渲染上限成了新的失败面**：审计发现 6 条事实"能回到原文却读不到"——5 条被单块
  1500 字符的**静默**上限挡住、1 条被 80 事件上限挡住。这两条上限已删（改按行分页），
  过程见[渲染静默截断那篇](../bug-fix/2026-09-29-silent-render-truncation.md)。
- **读别的巨型会话要重放整份日志**（实测 54 MB → 2.3 s）：已卸载到工作线程不阻塞循环，
  但同一会话连读两次会付两遍。
- **`AGENTS.md` 里的落地规则曾经模型看不到**（超注入预算被截断），过程见
  [注入预算那篇](../process/2026-09-29-agents-md-injection-budget.md)。
