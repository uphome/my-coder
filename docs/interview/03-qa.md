## A. 三层叙事

### A1. 六十秒版（电梯）

> 我写了一个 Python 的本地编码 agent 框架，重点不是"再做一个 AI 应用"，而是**把 agent
> 框架本身讲清楚**。一句话概括：**日志是唯一事实源**——模型的记忆、待处理消息队列、
> 回合号、工具执行记录、模型路由，全都是 `.sessions/<id>.jsonl` 的**投影**，
> 所以"恢复"就是"重放日志"，没有第二份会漂移的状态。
>
> 围绕这句话有四个设计：**surface 投影**（只有三类事件能进模型上下文，痕迹数据进不了）、
> **被动状态机 + 双队列 inbox**（支持运行中插队）、**turn/step 两级循环**
> （step 严格等于一次模型请求）、**决策走钩子与注册声明**（循环里没有业务 `if`）。
>
> 它有 12 个真实工具、CLI 和 Web 两个宿主；Web 前端是零构建单页，状态同样是投影。
> 测试数量由门禁现场测量（3 条平台相关 skip；要报数先跑 `pytest --collect-only -q` 复核——
> 这个数字会变，写死在讲稿里迟早说错）。其中三个门禁把"分层依赖方向、文档预算、文档数字"
> 变成不可违反的断言；数字门禁只数 **git 跟踪**的测试文件，未跟踪的在途文件不算。

### A2. 三分钟版（加一条生命线 + 一个最硬的取舍 + 一个边界）

在 A1 之后接：

> 一条消息进来走十二跳：`followup` 造不可变消息 → inbox **先落 `agent/inbox/spliced`
> 再改内存** → `wake` 拍醒被动状态机 → `run_turn` 落 `turn/start`、**peek 后跑插件钩子
> 再一次性 claim + 落 `user/message`**（中间没有 `await`，所以取消不会让消息凭空消失）
> → 组请求（system + `derive_messages()` + 工具 schema）→ 落 `request/header` →
> 流式帧只喂 UI 不落盘 → `assistant/message` → 工具按声明分组执行、`tool/result`
> **按模型顺序**落盘 → 回到外层循环再 claim → `turn/end`。
>
> 最硬的一个取舍是 **step 的粒度**。我一开始把一个"步"定义成整段工具循环，结果用户
> 插队的消息要等整段跑完才能被认领——实测一条插队消息在队列里躺了 2 分 40 秒，期间
> 50 多次工具调用，最后被当未处理输入清掉。改成"一步 = 一次模型请求"之后，工具循环由
> 外层 `run_turn` 驱动，每轮开头都 claim，插队延迟从"整段工具循环"降到"一次模型往返"。
> 代价是日志事件变细，`step/start` 与 `request/header` 变成 1:1。
>
> 边界我也清楚：**它不是 OS 级沙箱**。路径边界是纯用户态的归一化 + 前缀匹配，
> `bash` 的命令本身不过沙箱，只有 `cwd` 受限；真正的刹车是审批门。要上生产得先做
> 平台级沙箱（Windows token / Linux bwrap / macOS seatbelt），这也是我明确写在
> README 里的安全警告。

### A3. 十分钟版

按 [`01-tour.md`](01-tour.md) 的一页纸讲：先画六层与依赖方向 → 再讲一条消息的十二跳 →
然后挑三个机制展开（surface 与 replace 的位置语义 / 工具并发四条规则 / 压缩与召回）→
最后讲门禁与边界。**讲的过程中主动给文件名和测试名**，这是"我真的做过"的信号。

## B. 追问链（二十题）

### 定位与取舍

**B1. 和 LangChain / opencode 什么关系？为什么自己做？**

起点是 deepseek-harness 的核心架构（日志唯一事实源、被动状态机、钩子），我用 Python
重写，并且**对照了 PI 与 opencode 的取舍**——调研档案在 `docs/prior-art.md`。
自己做的理由：这些机制的价值在细节（比如"入队即记账"的顺序、`replace` 的位置语义），
用框架只能看到 API，看不到为什么。同时刻意**不像框架那样做抽象**：没有 provider 抽象、
没有持久化后端抽象——只有一个实现时，抽象是空壳。

> 追问："所以你是复刻？"——不是。有三处可以举证的不同（对照的是我调研时的 DSH 版本）：
> ① 增加了 `offload` 这一轴（Python 侧问题：同步 executor 会让 `asyncio.wait_for` 超时永不触发，Node 那边不存在）；
> ② 会话格式版本 + 未知事件 fail-closed 是自己设计的一套；
> ③ 上下文召回的三层结构是按"压缩不删数据"这个前提重新推的。

**B2. "六层"还是"四层"？**

六层是现在的事实：`values(0) → capability(1) → state(2) → runtime(3) → app/tools(4) →
web/cli(5)`，"四层"是历史叫法，指的是框架本体（values/capability/state/runtime）。
权威定义是 `tests/test_architecture.py` 的 `LAYERS` 字典——**不是文档**，
因为文档已经漂过（README 写六层、`architecture.md` 的 §2 标题仍写"四层单向依赖"）。

**B3. 这个项目最大的技术风险是什么？**

安全边界。工具沙箱是"防误用保险"而不是"防恶意"：工作区内全裸、TOCTOU 不设防、
`bash` 的命令本身无法校验路径。README 里明确写了这一点。要真做安全，路径校验必须
下沉到 OS 级（restricted token / bwrap / seatbelt），并且 `bash` 后端要可替换。

### 日志与记忆

**B4. 日志是唯一事实源，那内存里的 `Session` 对象算什么？**

算**缓存与投影**：`_log` 是事件本体，`_surface` 只是 seq 的索引列表（不存事件），
`derive_messages()` 是纯函数投影。所以"内存状态"永远可以由日志重建，
反过来不成立——这就是为什么它敢在崩溃后只靠重放恢复。

**B5. 为什么 `derive_messages()` 必须是纯函数？**

三个好处：恢复 = 重放（不需要写恢复代码）；同一段日志永远折出同一份记忆
（可复现、可测试）；`--resume` 与首次运行走同一条路径（不会"恢复后行为和首次不一样"）。
代价是所有"记忆"的来源都被限制在 surface 事件里，任何新状态想被模型看见就必须先设计成事件。

**B6. 日志越来越大怎么办？**

三层措施，都是实测驱动的：

1. **帧不落盘**：流式帧走 `emit_stream` 瞬时通道，每步只落一条汇总。原来 425,854 行里
   98.9% 是帧，改造后约 4,530 行，内容完整性有机械证明（帧拼接 == 落盘正文/参数/思维链）。
2. **重放时整类跳帧**：`Session.from_path(skip_types=…)` 直接不解析帧的 payload。
3. **访问器分层**：`events` 按变更缓存（返回不可变 tuple）、`event_count` O(1)、
   `events_since(i)` 只拷贝增量；稀疏日志用 `_sparse` 映射 + `_next_seq` 游标，
   保证跳帧后 `seq` 不重复。

**B7. 事件格式升级怎么办？**

会话头带 `format_version`，读取**按方向判**：更高版本 → 拒绝（明确告诉用户要升级，
与"文件损坏"分开）；相等 → 正常；更旧 → 读进来。**词汇增长不 bump 版本**，
新事件类型标 `ignorable: true`，旧读取者跳过、其余照常重建。
未知事件默认是**拒绝**而不是忽略——"忘标记导致过度拒绝"远好于"默认忽略导致静默恢复
出一份被掏空的会话"。

### 循环与状态机

**B8. 为什么 agent 是被动的？**

因为"谁在驱动"决定了并发与取消的复杂度。被动状态机的形状是
`idle --wake--> running --跑空 inbox--> idle`：忙时拍不醒就置标记，回 idle 的瞬间补拉；
`when_idle` 是 do/while 语义，保证"空闲"是稳定收敛的状态。所有输入都进 inbox，
没有第二条"直接调用执行"的路径。

**B9. 两层循环各自回答什么问题？**

外层 `run_turn` 回答"**还有没有任务**"（claim 批次、什么时候收尾），
内层 `_run_step` 回答"**这一次请求得到什么**"（一次模型请求 + 它发起的工具调用）。
合在一起就退化成"整段工具循环算一步"——那正是插队失效的原因。

**B10. 插队消息怎么保证不丢、不乱？**

- **不丢**：两个 `await`（`pre_step` 与 `request` 钩子）都在 `claim` **之前**，而
  `claim → step/start → user/message` 之间没有 `await`；取消点落在钩子里时队列一个字没动。
- **不乱**：未 claim 的消息没有 seq，所以前端不猜位置——`queued` 进队列区、
  `steering` 恒定贴尾；claim 后靠 `rpc_id` 提交身份与本地回显原子交接。

**B11. 取消是怎么传播的？**

`asyncio.CancelledError` 扮演 AbortSignal：`cancel() → driver.cancel() →` 沿 await 链
穿过 `_run_one → _run_group → _run_step → run_turn`。**每一层只记账、不拦截**：
`_run_group` 补合成结果、`run_turn` 记 `turn/end{aborted}` 后重新抛出、`_kick` 在边界吞掉回落 idle。
不补记账的后果很具体：日志会留下"带 `tool_calls` 的 assistant 消息却没有结果"，
下一轮请求直接 400。

### 工具与并发

**B12. 工具失败为什么不当异常抛？**

因为"失败"是模型能理解并修复的输入。四层兜底：坏 JSON（连 execute 都不进）、
参数校验（缺 required / 多参数）、执行抛异常、超时。全部降级成 `is_error` 结果。
唯一能穿过的是用户取消——那是控制流，不是失败。

**B13. 并发的判据是什么？**

**副作用，不是快慢**，而且**许可必须声明**：`ToolSpec.execution_mode` 默认
`'sequential'`，只有显式声明 `'parallel'` 才进并发池；未注册的工具名按 fail-closed
当独占（在 `mode()` 里不能抛 `KeyError`，否则执行阶段的降级兜底永远没机会跑）。
分组按**连续段**：并行段撞上独占调用就停手，剩下的重新分类。

**B14. `offload` 和 `execution_mode` 有什么区别？**

两根正交的轴：前者回答"会不会阻塞事件循环"，后者回答"能不能与其他调用并发"。
`read_file` 两者都是（纯读 + 同步盘 I/O）；`todo_write` 两者都不是；
`bash` 不并发但本身是异步（自带挂起点）。不卸载的同步 executor 会让
`asyncio.wait_for` 的超时**永远不触发**——协程体一口气跑完才还控制权，定时器没机会执行。

**B15. 崩溃留下的"悬空工具调用"怎么办？**

恢复入口（重放后、`bind_store` 后）扫一遍**投影**，给缺结果的调用补 `is_error` 合成结果，
并**先落一条 `session/repaired` 痕迹**说明这次自愈。刻意不在请求构造时补占位消息——
那会抹掉"这里断过"这个事实。修复是持久化的（写日志）且幂等。

**B16. 用户拒绝审批之后呢？**

拒绝不是失败：落 `tool/skipped` 痕迹（审计）+ 一条 `is_error` 结果告诉模型"没执行"。
模型必须看到"没执行"，否则会以为自己跑过了；然后它自己换方案，循环继续。

### 上下文

**B17. 压缩怎么做的？为什么是四步事务？**

`start`（加锁）→ `replace`（checkpoint 以 `user/message` + `surface_op='replace'` 原位
顶替旧回合）→ `summary`（审计：摘要全文、遮蔽范围、文件操作）→ `end`（成功失败都落）。
顺序是 review 改出来的：**先 replace 后 summary**，这样 replace 失败不会留下一份
"看起来压过了"的假审计。（这条的原始记录在 `tests/test_compaction_transaction.py`
的文件头，它写明是 review 后补的；`compaction.py` 的顶部注释与 `run_compaction`
docstring 现在也写的是实际顺序 `start → replace → summary → end`。）触发有两条：溢出恢复（模型报上下文过长 → `request_error`
钩子压缩后重试）与阈值自动压缩（回合结束后量上下文，默认窗口一半）。

> 追问："为什么要加锁/互斥？"——压缩要动 surface，必须串行；而且压缩请求本身也吃上下文，
> 并发压缩会互相把对方刚删掉的东西再算一遍。

**B18. 压缩把细节丢了怎么办？**

**压缩不是删除**：`replace` 只动 surface 索引，日志一个字不改。所以补三层召回：
L0 会话目录（每请求叠在状态栏）、L1 用户话清单（`session_manifest`，真人发言 + 每回合足迹）、
L2 回合明细（`read_turn`，按行分页、超限明说）。
**不做相关性排序**：语料是自述的时间线，模型看清单自己挑回合，比任何打分都准。
每请求路径不许碰整表——这里踩过四层 O(n)，从 278 ms 降到 0.1–0.2 ms。

**B19. 为什么 `AGENTS.md` 进 system，而 todo 状态进 messages 末尾？**

判据是**变化频率**。规则类内容会话内几乎不变 → 进 system 的 live 段，字节稳定，
不打断前缀缓存；运行时状态每步都可能变 → 作为合成 user 消息贴 messages 末尾
（不进日志、不进 `derive_messages`，但贡献者必须是日志投影的纯函数，所以可重建）。
放反了会每请求打碎一次缓存前缀。

**B20. "读不到"和"不存在"为什么要分开？**

两态会逼着模型在假前提上行动：把"读不到"渲染成"没有"，它会提议创建一份其实已经存在
（只是权限/断链/同名目录导致读不到）的约定。所以是三态：确认存在 / 确认不存在 /
读不到（`files="unreadable"` + "内容未知，不要当成没有约定"）。
实现上有两个坑：`lstat` 再 `stat`（断链 ≠ 不存在），以及**读完再取一次缓存键**
（读到半截会被缓存住并持续服务）。

## C. 压力问题

**C1. "这项目是不是把 DSH 抄了一遍？"**

起步确实是对着 DSH 的架构学。但能拿出来的自证有三样：① 有 17 篇设计记录，
每篇记的是**当时的替代方案与被否决的理由**，抄不会产生这些；② 有几处是 DSH 没有的
（`offload` 轴、会话格式版本与未知事件守卫、召回三层的形状）；③ 有几个 bug 只有自己写过
才会踩到（`replace` 的位置语义、跳帧后的重复 seq、取消时消息三处都不在）。
如果要更硬的证据，可以说："你可以随便挑一个机制，我讲它的失败场景和对应的回归测试。"

**C2. "如果让你重做，你会改什么？"**

三件：① 先把"事件词汇表"定成显式 schema（现在 `append` 不校验类型是否在闭集里，
拼错的新类型能写进去，读取时才被拒）；② 会话日志从一开始就按冷热分层设计
（帧时代的日志需要跳帧才能读）；③ 日志行扫描从第一天就只留一份共享实现
（这次发现 `recall` 与 web 列表各有一份、且都依赖 JSON 分隔符——已合并，
但这本可以一开始就不重复）。

**C3. "这个能上生产吗？"**

不能，差三块：OS 级沙箱、多 worker 下的并发正确性（压缩互斥和会话创建的部分锁只在
进程内）、以及可观测性（目前靠日志 + 一个教学脚本，没有指标与告警）。定位是个人工具
与教学实现。

**C4. "你怎么证明它真的能干活？"**

四层：单元/集成测试（含并发、取消、崩溃自愈的回归）；`--fake` 脚本化模型离线跑通全链路；
一次真模型端到端验收（读 → 搜 → 分页 → 执行 → 批准 → 验证 → 报告；记录在 `NEXT_STEPS.md`，
要 API key，没有留下可复跑的证据）；以及一个召回评测
（受控构造数据 + 三臂对照 + 可恢复性审计）。门槛是"三绿才提交"：ruff + mypy + pytest。

**C5. "LLM 应用的非确定性怎么测？"**

把不确定性挡在边界外：`FakeLlm` 是脚本化的，循环层只认 `StreamChunk` 契约；
决策点全部是注入的钩子（测试注入假实现）；行为断言落在**日志事件序列**上
（不落在自然语言上）；web_search 用假 HTTP 层。真模型只用于验收，不用于断言。

**C6. "9 千行里你最自豪的是哪一段？"**

`_run_group`。它同时解决三个问题：并发许可（声明 + 连续段分组 + 池上限）、
落盘顺序（槽位 + 连续推进，谁先跑完不影响日志顺序）、取消（drain 已派发的调用、
认它的真结果，再给剩下的补合成结果，且挡住二次取消）。
近百行里每个分支都对应一个真实故障（三块机制各约二十行：并发许可、有序提交、取消补账）。

## D. 诚实边界

### D1. 明确不做（设计取舍，不是缺陷）

| 没做 | 前提 |
|---|---|
| OS 级沙箱 | bash 执行后端可替换 + 平台 API |
| 工作区热切换 | 先回答"旧目录内容算不算这个会话的记忆" |
| 会话日志按工作区分目录 | 等价于一次存储迁移 |
| 持久化后端抽象 | 要有第二个实现才不是空壳 |
| 按参数的并发谓词 | 只有静态声明 |
| max-tokens 粘性续写 | 回合语义要先区分"截断"与"取消" |
| web_fetch / 多搜索 provider | 抓正文是另一个能力 |
| RATE_LIMIT 退避 | `request_error` 钩子已被溢出恢复占用，要先定优先级 |
